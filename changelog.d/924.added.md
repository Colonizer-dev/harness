- **An org can narrow the exec policy its own colonies run under.** The exec policy already had an
  org layer in both runners, but nothing ever set it; a new `exec_policy` field in Org settings
  (`PUT /api/orgs/{org}`) is that layer, and the mothership passes it to a colony as
  `COLONIZER_EXEC_POLICY_ORG`. It layers between the install's `exec_policy` setting and a
  repository's own `.colonizer/exec-policy.json`, narrowing in both directions: rules can only
  remove permissions, never grant one the layer below has already refused. The field takes the same
  JSON a runner reads — an object with a `rules` array, at most 64 KiB, the same cap both runners put
  on a layer — and is refused at save time
  rather than dropped at boot, where a malformed layer is only a warning. An org whose colonies
  launch on an agent module that does not apply the policy refuse to boot while any layer is set,
  naming this one alongside the install's and the repo's, exactly as before. Editable in the
  cockpit's org dialog under Colonies, alongside Stack. ([#924])
