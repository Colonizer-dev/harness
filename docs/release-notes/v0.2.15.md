- **The observability pane shows the exporter's health, guides the common backends, and asks before it sends conversation content.** Settings → Modules → Observability gains a health card: one row per signal (logs, traces, metrics) labelled Sending, Backing off, Unauthorized or Off, with the retry countdown or the last error beside it, a summary of the backlog, records sent and the last success, and a line saying where each setting came from (the module settings, an environment variable, or the built-in default). - **The mothership now keeps a log of its own, and the exporter can ship it.** Everything the running harness has to say — a provider went out of quota, a fleet file did not parse, a mesh policy could not be written, the storage alert fired — is written as redacted JSON lines to `<data>/logs/mothership.jsonl`, which the observability add-on tails like the other ledgers. Each line is one object with a millisecond RFC 3339 `ts`, the lowercase `level`, the module `target`, the `message`, and every structured field beside it under `fields`; the file rolls to `mothership.jsonl.1` at 8 MB, one generation only, so at most two files ever exist, and every line goes through the same secret redaction as the activity log before it lands.
- **New mothership diagnostics can no longer bypass the log: `eprintln!` is forbidden.** The remaining ~170 `eprintln!` sites across the mothership (redteam, usage, remote, claims, the loops, github, phone and the long tail) now emit `tracing` events with structured fields, so they land in the mothership log and the exporter instead of only the terminal; a workspace `clippy.toml` rejects `std::eprintln`, with reason-commented allowances for the CLI's own output, the first-start usage notice, the two prints that happen before the log exists, and the guest agentd and observability add-on, which keep their stderr. ([#857](https://github.com/Colonizer-dev/harness/issues/857))
- **`colonizer observability backfill`: replay the history a destination never received.** A new backend starts at "now", and the live exporter's backlog only reaches back so far — everything older sat on disk and never left the machine. The new command counts that history first (`--dry-run`: per signal and per org, ledger bytes, an estimated encoded volume; nothing sent, nothing written) and then replays it through the supervised add-on at a bounded rate (`--rate`, default 500 records/s), with the same record and span ids the live exporter would have produced, never moving the live cursors. `GET /api/observability/status` carries the replay's progress as `backfill` while it runs, `DELETE /api/observability/backfill` stops it within one tick, and an interrupted run resumes where it stopped. The `POST`/`DELETE` routes are owner-only. ([#858](https://github.com/Colonizer-dev/harness/issues/858))
- **Four Grafana dashboards for the observability stack, provisioned from `examples/observability/` and kept honest by a lint.** Motherships & fleet, Colony, Gateway & spend and Agent behaviour ship as dashboard JSONs under `examples/observability/grafana/dashboards/`, with the datasource provisioning that pins the uids (`colonizer-prom`, `colonizer-loki`, `colonizer-tempo`) they all query — mount the two directories and a Grafana loads them into a "Colonizer" folder, against the local stack or a remote one. `scripts/check-dashboards.mjs` runs in CI's `scripts` job and fails a dashboard that does not parse, queries a metric name neither catalogue lists or a datasource uid nothing provisions, repeats a panel id, or hard-codes a colony id — the shape of one is any 8-hex-digit string — so a renamed metric or a pasted id fails the pull request instead of showing a blank panel later; `scripts/test/check-dashboards.test.mjs` tests the checker. The Colony dashboard's content panel counts content log records and reads "Content export is off for this org" while they are absent, which is honest: content log records do not exist in this build yet (issue #848). The local compose stack that feeds the dashboards — collector, Prometheus, Loki, Tempo — lands with issue #862. See [the dashboards page](docs/observability/dashboards.md). ([#863](https://github.com/Colonizer-dev/harness/issues/863))
- **Observability export is now proven against a real OpenTelemetry Collector in CI, not only against fakes and goldens.** A new `observability-conformance` workflow builds a digest-pinned `otel/opentelemetry-collector-contrib` image from `.github/ci/otel-collector/` (dependabot bumps the digest weekly) and runs the add-on's one ignored conformance test against it: trace and span ids arrive as the spec's lowercase hex with parent links intact, resource attributes and per-signal record counts match what the exporter reports sent, the secret canaries never reach the stored output in any form, the closed content gate drops content-tier text (and an open, test-only one redacts secrets to their marks), and the committed OTLP/JSON goldens round-trip through the collector's own file receiver. The run covers OTLP/HTTP protobuf and JSON plus gRPC behind the `otlp-grpc` feature, runs on pull requests and pushes touching the add-on, the mothership's observability module, the examples or the collector config, and can be run locally with Docker or a plain `otelcol-contrib` binary — `OTEL_CONFORMANCE_DEMO=break-ids` or `leak-canary` deliberately fails it to show the checks bite. - **A public, sanitized activity feed, so a colony can be drawn as an animated entity somewhere that is not the cockpit.** `GET /api/public/feed` answers the last events plus the colonies still in flight; `GET /api/public/feed/stream` answers the same events as Server-Sent Events and resumes from `Last-Event-ID` with no gap (and says so when the log has rotated past the point asked for). Both are off until `[public_feed] enabled = true` names the repositories to publish in `colonizer.toml`, and a line whose repository is not on that list is dropped rather than published with the name removed. The event is a closed allowlist of ten fields with a test that pins the serialized key set: an event carries an id, a kind, a pseudonym of the colony, the repository, the issue number, a pull-request URL, a status word, a time, a host id and a reserved intensity that is unset — a colony's task, a question's text, a failure's reason, a path and a cost are never read from the activity log at all, and no title of any kind is published, because the log's `title` falls back to the task and the colony record's `issue_title` is whatever an operator typed. The pull-request URL is validated as an http(s) URL before it is published, and the feed is refused over the remote tunnel, where an address allowlist could not mean anything. The feed authenticates with its own read-only keys (`colonizer feed-key create --name … --ip 203.0.113.0/24 --rate 30`, `list`, `revoke`), stored in `<config_dir>/feed-keys.json` as a SHA-256 with the plaintext printed once, and enforces a per-key address allowlist read from the socket — never from `X-Forwarded-For`, which is a claim the client makes about itself — and a per-key rate limit. - **A launch can carry your own name for the colony, and a retried launch is not a second colony.** `POST /api/sessions` takes an optional `external_ref` — a name your own system already keeps, up to 200 printable characters — which is recorded on the colony once and never changed, and `GET /api/sessions` takes `?external_ref=` and `?origin=` filters that narrow the list (they compose with each other and with `limit`/`cursor`, and both the JSON API and `GET /uhp/v1/sessions` answer them). `POST /api/sessions` also honours an `Idempotency-Key` header: sending the same key again answers the colony that key created — after a restart too, because the key is kept with the colony — rather than starting a second one, and the replay is not charged against the token's launch caps. - **A colonizer commit now says which Colonizer wrote it, through which settler, on which model.** Every commit and pull request Colonizer publishes carries `Colonizer-Version`, `Colonizer-Settler` and `Colonizer-Model` trailers on the commit, and the same three facts as a small table in the pull request body, so a maintainer can tell the automated work apart at a glance and filter for it with an ordinary `git log --grep` or a search over trailers — no more opening each pull request to find out. - **A resolved-rate report from the bench, counting PR opened, tests green and merged separately, split by harness · model.** `node scripts/bench.mjs rate [bench-run.json …] [--data DIR] [--json]` unions the bench run files named on the command line with the real colony session store at `<data dir>/sessions.json` — the same resolution rule `jev`, `brief` and `routing` use — and prints one Markdown table by harness · model and source, with an `overall` row that pools counts rather than averaging per-group rates. `--json` emits the same report in a stable order, so a CI job can regenerate it and diff it between revisions.
