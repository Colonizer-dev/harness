# Colonizer v0.2.16

## What's new

- **A fleet member's observability is part of its health badge.** A member's reduced
- **Observability: a runnable local Grafana stack, per-backend recipes, and the limits and costs written down.** `examples/observability/grafana/` gains a compose stack — Alloy as the collector, Loki, Tempo, Prometheus and Grafana with provisioned dashboards — that the exporter reaches with one loopback endpoint, plus the Alloy, Loki and Tempo configs tuned to the exporter's caps, a README walking through it, and a CI check of those example configs. Two docs pages join the observability guide: [Backend recipes](docs/observability/backends.md), with the endpoint, the header and the ingest limits for Grafana Cloud, Datadog, Honeycomb, Elastic, SigNoz, New Relic, the local stack and a plain `otelcol-contrib` collector, and [Limits and cost](docs/observability/limits-and-cost.md), which maps each backend limit to the exporter setting that stays under it, reports the volume measured on the repository's fixtures (per record, per trace and per colony-hour) with the method, and lists the levers — sampling, the stream switches, the metrics interval, gzip — that lower the bill. ([#862](https://github.com/Colonizer-dev/harness/issues/862))
- **mattpocock-skills: an optional thirteen-skill engineering pack, staged non-interactively with its setup pre-seeded.** [mattpocock/skills](https://github.com/mattpocock/skills) (v1.3.1, MIT) is vendored as `mattpocock-skills`, off by default like ponytail and security-audit: an operator adds it to the claude-code module's Skillsets list, and a new **mattpocock-skills allowlist** setting narrows it to a comma-separated subset of its thirteen skills (`tdd`, `diagnosing-bugs`, `code-review`, `to-spec`, `implement-spec`, `to-tickets`, `triage`, `improve-codebase-architecture`, `codebase-design`, `domain-modeling`, `pr`, `handoff`, `writing-for-agents`). Only that curated set is staged — each skill with the sibling files it reads, minus its Codex stub — and staging is an allowlist that fails on any other skill: the interactive ones (`grill-me` and friends) would stall a colony on an interview, and `setup-matt-pocock-skills` is never staged because the runner pre-seeds the per-repo configuration it would write (issue tracker, triage labels, domain docs) in the system prompt, where the consumer skills find it — so no setup prompt ever reaches the cockpit, and a PreToolUse hook refuses the excluded names and any skill the allowlist does not name. Where a skill conflicts with how a colony runs, the colony's rules are stated in the prompt and win: no merging, pushing or branch-making, the pull request description in the colony's pr.md format, and assumptions stated instead of confirmation rounds. Two of the thirteen (`code-review`, `pr`) share their names with ECC's commands; the namespaced addresses (`mattpocock-skills:code-review` vs `ecc:code-review`) keep them distinct, and both packs can be enabled together. ([#1016](https://github.com/Colonizer-dev/harness/issues/1016))
