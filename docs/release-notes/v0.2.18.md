- **Stacked colonies no longer cascade into failure when their parent fails; they now wait for recovery.** Colonies stacked on a parent that entered a failed state used to immediately fail themselves, killing entire dependency chains with a single failed parent. Now, when a parent enters a failed state, its children transition to a waiting state instead, pausing their work until the parent recovers. When the parent recovers, waiting children automatically resume from where they left off, allowing the full stack to continue working together. This prevents the loss of work in multi-level colony stacks and enables recovery scenarios where a transient parent failure can be resolved without restarting all dependent colonies. - **Colonies park when the Claude account and its fallback's provider are both out of quota.** Where before a running colony kept its microVM and had its agent re-ask every minute, each request coming back `quota_exhausted`, the queue's 5 s tick now parks a colony whose whole provider chain — the Claude account and every provider its `allowed_providers` list can reach — is out, releases the slot and, under the usual `discard_vm`, removes the microVM. The park names the exhausted provider and the earliest reset in the chain, so the colony rejoins the queue on its own when either plan refills. The hosts are clamped by the fleet floor like module hosts. In `open` mode they are not a fence (the `public` profile covers them); a per-pack fence in open mode is future work. - **Autopilot no longer publishes, or releases the issue as "no changes", while the agent's background subagents are still running.** When a lead agent launches background subagents with the Agent or Task tools, autopilot waits for them to settle before publishing the PR, even if the PR description is already written. This prevents premature releases while the subagents are still making changes. Errors are not blocked by subagents: a turn that ends with an error is held or retried immediately. An empty branch whose PR description names changed files is now held as contradicted, rather than published as "no changes" ([#1268](https://github.com/Colonizer-dev/harness/issues/1268)).
- **context-mode, an opt-in third-party module, with the exec policy enforced on its tools.** Organisation settings take a `context_mode` of `off` (the default), `shadow` or `on`, passed to the colony as `COLONIZER_CONTEXT_MODE`. In `on`, the Claude Code runner registers the [context-mode](https://github.com/mksglu/context-mode) MCP server only from an operator-installed copy whose `package.json` matches the pin in `modules/agents/claude-code/context-mode.json` (1.0.169, sha256 and npm integrity, ELv2 — never bundled), with its data kept in the colony guest's `~/.colonizer/context-mode` rather than the shared `~/.claude`. `shadow` is accepted but does nothing yet. Whatever the mode, the exec-policy hook now also covers `ctx_execute`, `ctx_execute_file` and `ctx_batch_execute`: shell code is judged exactly as the same Bash command, other languages as an inline script, every batch command separately with the strictest decision winning, and malformed input, `..` paths and `ctx_upgrade` are refused. ([#1273](https://github.com/Colonizer-dev/harness/issues/1273))
- **Org dashboard: Cost per merged PR now reads the same window as the Spend tile, not the all-time session rollup.** When the live-session rollup was close to zero but the spend history showed measured activity, the Cost per merged PR tile could contradict the Spend tile or round to "$0.00". The tile now divides the period spend (from `/api/spend/history`, the same value the Spend tile shows) by the number of PRs merged in that same date range (not all-time), so the two tiles always cover the same window and can never contradict each other. The sub-line now says "N merged in range" instead of "N merged", and the tile shows "—" with an explanatory note when nothing merged in the period but spend was measured (or when spend is unmeasured). ([#1275](https://github.com/Colonizer-dev/harness/issues/1275))
- **Input screening detects hidden text in GitHub issues and comments at launch.** The `promptdecode` org setting (`off` by default) runs a local scanner for zero-width characters, tag runs, bidi controls, HTML comments, and base64 payloads: `off` skips scanning; `shadow` records findings in the session log and ledger without mutating the issue; `on` removes hidden text and appends a visible note. The screening runs before the prompt is built, using a local decoder until the promptdecode CLI ships; PR comments, fetched pages, diffs, and the cockpit card are future slices. ([#1277](https://github.com/Colonizer-dev/harness/issues/1277))
- **Red-team: detects repository artifacts that would change the colony's PATH (executable shims, direnv, version managers, Makefiles).** The colony ledger now flags repositories with committed `bin/cargo`, `.envrc`, `Makefile` with PATH assignments, and similar artifacts that hostile repos use to fool agents. Verification gates are unaffected: they trust the VM's reported exit code, not fabricated output. PATH stays pinned by the image. ([#1278](https://github.com/Colonizer-dev/harness/issues/1278))

The providers page UI now clearly distinguishes providers without quota probe support by showing "no balance API" instead of the generic "balance unknown", making it easier for operators to understand which providers support balance queries and which do not. The verdict now only shows on colonies that are queued or blocked waiting for a slot; running and working colonies no longer display a placement message. - **Prevent infinite retries on corrupted git repository mirrors; automatically repair with reclone and set attention on unrecoverable corruption.** When a git mirror became corrupted due to disk errors mid-write, every colony booting against it would retry infinitely, burning through the retry budget without progress. Now, `sync_repo` climbs a three-rung repair ladder: first, corrupt loose objects are cleaned locally and a fetch is retried; second, if still failing, the entire mirror is re-cloned from GitHub and the fetch retried; finally, if the re-clone's fetch fails, the operator is notified via `mirror_needs_attention` and the colony enters an attention state to free its microVM slot. The corruption detection now covers additional git error messages (`did not send all necessary objects`, `nonexistent object`, `missing object`, `broken ref`) to catch corrupted refs in addition to corrupted objects. When mirror corruption is unrecoverable, the session's `attention` field is set with reason `repo_cache_corruption_unrecoverable` so it doesn't silently hold a slot. ([#1319](https://github.com/Colonizer-dev/harness/issues/1319))
- **The agent prompt explains why a nested clone's `.git/config` and hooks are read-only, and how to clone without defeating the mount.** A `git clone` into the workspace (e.g. a build cloning a data repo into a gitignored dir) failed on the path policy's read-only binds; an agent that didn't know why tried to `umount` them and was held as `control_defeat`. The prompt now says why these binds exist, names the supported route (`git clone --separate-git-dir=/tmp/<name>.git` to keep the git dir outside the workspace, or clone outside it entirely), and forbids trying to unmount. The hold itself is unchanged — a protection mount is real and trying to defeat it is real `control_defeat` — and nested clones in gitignored dirs stay protected. ([#1320](https://github.com/Colonizer-dev/harness/issues/1320))
